## 3. НАЗНАЧЕНИЕ РАЗРАБОТКИ

### 3.1. Назначение и цели создания Системы
3.1.1. Система должна обеспечивать автоматизацию полного цикла работы исследователя с томографическими данными: загрузку и хранение проектов, двумерную и трёхмерную визуализацию матричных данных, применение фильтров и геометрических преобразований, выполнение измерений (профили, выделения), сохранение результатов, а также конструирование и исполнение последовательностей обработки (workflow).

3.1.2. Цели создания Системы:
- снижение трудоёмкости и времени рутинной обработки томограмм;
- стандартизация типовых последовательностей обработки (конструктор графов);
- сохранение воспроизводимости результатов (история операций, серверное хранение версий);
- отказ от установки специализированного ПО на рабочих местах (эксплуатация через веб-браузер).

Количественные показатели целевых эффектов — **[ТУ]**.

### 3.2. Перечень объектов, для которых предназначена Система
Файлы томографических срезов в формате `.tpt` (текстовое представление числовой матрицы), матрицы NumPy (`.npy`), метаданные проектов (JSON). Иные входные форматы — **[ТУ]**.

### 3.3. Уровень значимости
Система относится к программам для научных целей; ответственность за интерпретацию результатов обработки несёт пользователь-оператор. Требования по особым видам безопасности (атомная техника, оборона и т. п.) не предъявляются — **[ТУ: подтвердить]**.

### 3.4. Категория качества
Система должна соответствовать категории качества **1** по ГОСТ 19.104-78 (высокая надёжность, интенсивная эксплуатация) — **[ТУ: утвердить категорию]**.

### 3.5. Условия эксплуатации
Эксплуатация в помещении с сетевым доступом рабочих мест к серверу приложения (Flask, TCP-порт 15404) и объектному хранилищу MinIO. Окружающие условия — стандартные для офисных/лабораторных помещений. Особые климатические/механические требования к аппаратным средствам не предъявляются — **[ТУ: подтвердить]**.

4.3.7.1. В поставленной реализации на уровне приложения аутентификация не проверяется: из заголовка `Authorization` (Basic) извлекается только логин; пароли не верифицируются; ролей и разграничения прав доступа нет; доступ к данным любого проекта возможен из любого браузера сети.
4.3.7.2. Реализованы технические меры: валидация путей объектов MinIO от directory traversal; белый список расширений загружаемых файлов (`.tpt`); ограничение размера запроса.
4.3.7.3. **Требование на доработку:** перед вводом в промышленную эксплуатацию Система должна быть обеспечена механизмом аутентификации (источник заголовка `Authorization` — внешний прокси/IAM — **[ТУ]**) и разграничением прав доступа по ролям. Модель угроз, класс защищённости и нормативные документы (ГОСТ Р 50922, руководящие документы ФСТЭК) — **[ТУ]**. До реализации данного требования эксплуатация допускается только в доверенном сегменте сети.

#### 4.3.8. Стойчивость к нестандартным воздействиям
Стойкость к сбоям питания сервера обеспечивается внешними средствами (ИБП) — **[ТУ]**; после рестарта состояния вкладок браузера восстанавливаются из кэша IndexedDB и серверной истории файла. Требование к работе при недоступности MinIO: сервис возвращает JSON с полем `error` и кодом 500, данные клиентов не повреждаются. Иные воздействия — **[ТУ]**.
